# 多角色需求研讨与文档收口

## 目标
把协作群里的产品或系统讨论，收成一份可版本管理的现行需求/方案文档：共识写清楚，角色间分歧被裁定或单独列出，未决项不伪装成已确认结论；测试与编码在阻塞项确认前，不把一期范围写死。已确认或已演示的分期，不因后续新想法被悄悄扩大或回改。

## 步骤
1. 先定核心定位，再进技术方案。协调方（或最先响应的角色）用一两句话抓住「要做成什么、不要做成什么」，再请研究员分析：核心对象与关系、系统边界、模块划分、可落地路径和分期建议。同时请测试员提出必须先能验收的问题，请编码助手列出开工前要定的对接、技术栈与明确不做的事。
2. 各角色在群里并行补充，不要只在单聊里交接。研究员给出对象模型与分期；编码助手给出实现路径、边界和不做事项；测试员给出可验收条件，并要求每期写清范围内与不在范围内的内容。
3. 用户要求出需求文档，或讨论已够收口时，由文档管理员整理现行稿发给用户，并按已有档案规范归档。文档至少覆盖：
   - 已达成共识的目标、对象模型、系统边界、明确不做的事
   - 角色之间的分期或其他分歧：在文档里裁定并写清结论和理由；暂时不能裁定的，明确标成待决
   - 未决项单独成节，并标出哪些未决会阻止一期边界封口
   - 每期的范围内、不在范围内，以及一期验收标准
   - 未经提出人确认但必须暂用的假设，写成默认假设，不得伪装成已确认结论
4. 做好版本管理：保留旧版备查；新版文首注明与旧文档的关系和现行稿标记；已有结论不覆盖，在文末追加变更记录。提出人就未决项拍板后再升版。每次入库或升版后回写档案索引。
5. 若现行稿已经存在，且其中某些分期已被提出人确认或已经演示过，提出人又补充新能力：先对照现行稿，分清哪些已经覆盖、哪些确属新增、哪些会扩大或回改已确认分期。已经覆盖的只指出出处，不重复立项；确属新增的收成下一期补充稿，不要回头改已确认或已演示分期的范围和接口。补充稿先交给提出人确认（包括其新加的约束）；确认后再发到协作群，由文档管理员并入现行稿并升版，旧版改为备查并回写索引。此前仍待确认的未决项继续单列，不视为本次已拍板，也不在这次升版里关闭。编码与测试只按新版中本期新增章节执行和写测试方案。升版时或刚升版后，其他角色可以补充实现口径（例如过滤字段、入口如何复用现有数据）；只要不再扩大或回改已确认范围，就写入本期章节，并标明这不是提出人的新确认，不得据此关闭仍待确认的未决项。若口径会扩大或回改已确认范围，仍先写成补充稿交提出人确认，不得直接改现行稿。接口若还要对齐，可写成默认假设并补接口说明，同样不得伪装成提出人已确认的结论。
6. 文档发出后，编码与测试先对照文档反馈缺口（例如验收口径遗漏），由文档管理员补进待确认项或升版。技术栈无另行指定时，编码助手可按文档中的默认栈准备领域模型或接口草案；但分期、权限等会阻止一期封口的事项未确认前，测试员不写死第一期测试方案，编码助手不把未决边界锁进实现。

## 注意
- 角色名称、协作群和档案路径以当时约定为准，不要写死某个助手的私有编号或个人目录。协调可以是独立角色，也可由文档管理员或提出人指定的人代行。
- 本技能只规范讨论如何收成文档，不把具体项目的定位、对象或技术栈写成必要步骤。
- 若尚未组建互补角色与共享档案，先按「多角色研发协作」就绪，再进入本流程。
