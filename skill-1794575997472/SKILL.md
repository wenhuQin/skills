# 验收后发布到私有仓库

## 目标
先按官方需求与测试方案完成功能验收，通过后再把已验收代码发布到指定 GitHub 仓库，并保证仓库在整个过程中保持私有。

## 步骤
1. 先验收、后发布。以仓库内的官方需求文档、已记录决策和测试方案为唯一执行依据。方案里尚未确认、但决策文档已写明默认的事项，按默认判定，不要因此把相关用例一律记为阻塞。逐条执行方案中的全部用例，不要只跑自动化测试；能补的自动化补上，保留命令输出或截图等证据，并把测试报告写入仓库文档。通过标准若不成立，先在当期范围内修复并回归，再考虑发布。不要扩大范围，也不要在验收完成前推送。
2. 发布前确认目的仓库的访问权与可见性。用户要求仅自己可见或必须私有时：在任何推送之前用 API 核对仓库已是 private。若仍是 public，不要推送，即使只公开一瞬间也不行。
3. 常见的代码托管集成（例如 Cursor GitHub App）通常没有修改仓库可见性的权限，强行修改会被拒绝。不要反复试改可见性，也不要为改权限去创建文件或提交。请用户在 GitHub 仓库设置中自行改为 Private；用户确认后，再核对一次可见性，确认已私有后再推送。
4. 若可见性或授权暂时卡住，先把已验收源码打包作为中转产物：包含实现、文档（含测试报告）和测试；若 `.git` 体积不大可带上历史。排除 `node_modules`、构建产物、`.env` 和密钥。不要为了交差而推到仍公开的仓库。
5. 仓库已确认私有后，按远程现状选择推送方式：
   - 远程仍为空（无 commit）：把已验收历史原样推到默认分支（通常是 `main`），不要为此开拉取请求，也不要改写这段历史或额外加一个无关提交。
   - 远程已有出乎预期的提交（例如平台自动生成、仅含 README 的 Initial commit）：停止并报告，不要擅自 force-push。只有仓库主人明确批准覆盖当前默认分支，并且复核远程仍只是那份占位提交时，才允许针对这次替换做 force-push。若远程又出现其他新提交，停止并报告。
6. 推送后核对：目标分支指向预期提交，仓库仍为 private，且没有把密钥或依赖目录推上去。把仓库地址、提交 SHA 和可见性确认回报给用户。

## 注意
- 具体仓库名、分支和可见性范围以当时用户约定为准，不要写死在本技能里。
- 不要在公开状态下推送「先上去再改私有」。
- 未经明确批准，不要 force-push 覆盖已有历史。
