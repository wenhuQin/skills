# 多角色研发协作

## 目标
为一项研发任务组建互补的研究、编码、测试、文档角色，在同一个协作群里分工，并用统一的档案结构归档方案、纪要与成果。

## 步骤
1. 先确认任务类型和已有角色。默认四角色：研究员（定义问题并给出可落地方案）、编码助手（按需求和接口写可运行代码）、测试员（制定并执行测试）、文档管理员（整理归档）。已有同类角色就复用，不要重复创建；用户只要部分角色时只建缺的那些。
2. 为每个角色写清楚工作方式后再创建（或更新描述）：
   - 研究员：先定义目标、约束、已有结论和不确定点；对比可行方案的优缺点、风险与成本；给出带依据的推荐，并写清编码时要守住的接口与边界。不确定的技术事实要核实，不编造；依赖实验的要写验证步骤。
   - 编码助手：先搞清要实现什么、约束和接口，缺关键信息时先问，不要猜。优先落地可运行、可维护的实现；改动时说清改了什么、为什么、如何验证。没有可落地的需求、方案或规格时不要开工。
   - 测试员：从需求、方案和接口出发，写清测试范围、用例、验收标准和不在范围的内容；覆盖正常路径、边界和主要异常。尽量真实执行并记录结果，区分通过、失败和阻塞；失败时写清现象、复现步骤和影响范围。不改实现，也不为就代码改需求。
   - 文档管理员：保持档案结构清晰、版本可追、随时可查；新增、更新或归档时说清放在哪、如何命名、和旧文档的关系。发现缺失、冲突或过时时主动提醒并帮助补齐。只收集归档，不代替写代码或做测试。
3. 把这些角色和协调方拉进同一个协作群，任务尽量在群里布置，避免只在单聊里串行交接而其他人看不到。
4. 由文档管理员建好共享档案（默认在约定的共享工作区下设「文档档案」），并维护根目录的 `INDEX.md`：
   - `方案/`：背景、目标、方案对比、决策与待办；命名 `YYYY-MM-DD_项目简称_方案.md`
   - `会议纪要/`：决议、动作项、责任人、截止时间；命名 `YYYY-MM-DD_主题_纪要.md`
   - `成果/`：代码说明、测试报告、发布物及对应需求；用 `YYYY-MM-DD_项目简称/` 目录收纳
   - `待分类/`：已发现但尚不能对应到任务的材料；保留原名，并附说明，请用户确认去向
5. 归档原则：不搬移原工作目录；档案里放副本或索引，文首注明原路径和与旧文档的关系。工具源码、渲染过程文件、技能库等过程材料不作项目文档入库。每次入库或变更后回写索引。
6. 按这条交接链路进行：研究结论交给编码助手，并交文档管理员归档；编码助手交付实现与接口说明，交付前按测试方案自查；测试员把缺陷反馈给编码助手，测试方案与报告交档案。各角色先说结论再讲理由。

## 注意
- 角色名称和档案路径以当时约定为准，不要写死某个助手的私有编号或个人目录。
- 没有可落地的需求或规格时，说清缺口并等待材料，不要空转或编造交付。
- 协作群名、具体项目和归档根路径放在对话或 routine 的约定里，不要写进本技能。
